# AI API 보호·회원가입 동의 보완안

## AI 여행 일정 API — 권장 방향(아직 구현 전)

대상은 Express `POST /api/itineraries/generate`다. 로컬이음의 HOST Edge Function과 다른 API이며 현재 사용자 인증·요청 한도가 없다.

1. **로그인 회원만 생성:** Supabase `getUser`로 검증한 JWT의 사용자 ID를 사용한다. 비로그인/만료 토큰은 401로 차단하고 본문 userId나 이메일을 신뢰하지 않는다. 여행지 공개 조회는 계속 비회원이 사용할 수 있다.
2. **사용자별 동시 생성 1건:** 중복 클릭·여러 탭으로 AI 호출이 겹치지 않게 한다. 사용자에게 진행 중인 생성이 있음을 알린다.
3. **지속성 있는 요청 한도:** 초기 제안은 사용자당 시간당 10회다. 수치는 팀과 예산을 검토해 확정한다. Vercel 다중 인스턴스를 고려해 Supabase의 원자적 RPC로 슬롯/사용량을 관리한다. 프런트 버튼 비활성화나 서버 메모리 Map만으로 전역 한도가 보장된다고 주장하지 않는다.
4. **응답과 정리:** 한도 초과는 429와 Retry-After, 시간 초과는 명확한 안내로 처리한다. 생성 중 오류가 나도 동시 실행 잠금을 해제한다. 만료 잠금을 자동 회수하고 무제한 재시도로 AI 비용이 늘지 않게 한다.
5. **검증:** 비로그인/잘못된 JWT/타인 ID 위조/동시 2건/한도 초과/모델 장애 시 슬롯 해제/정상 회원 1건을 검증한다. 프롬프트·토큰·개인정보는 로그에 저장하지 않는다.

위 설계는 아직 API 코드나 DB에 적용하지 않았다. 사용량 테이블·RPC가 필요하므로 구체 SQL과 영향 범위를 별도로 검토·승인받는다. 운영 AI 키와 실제 생성 환경을 확인한 뒤 지연 구간도 함께 측정한다.

## 회원가입 동의 — 로컬 구현과 SQL 초안

- `/terms`, `/privacy`에 **검토용 초안**을 만들고 가입 화면에서 각각 별도 탭으로 연다. 문의 이메일은 사용자가 제공한 `beautimind01@gmail.com`이다. 운영 주체의 공식 명칭·보유/파기 기간·외부 처리/국외 이전 조건은 아직 확정하지 않았다.
- 필수 동의 두 항목을 각각 확인하고, `shared/servicePolicies.js`의 `2026-11-07-draft` 버전과 함께 Supabase Auth 신규가입 metadata로 전달한다.
- Auth metadata는 회원이 나중에 바꿀 수 있다. 이것만으로 변경 불가능한 동의 원본 기록이 완성됐다고 표시하지 않는다.
- [동의 SQL 초안](20261107_signup_consent.review.sql)은 새 `travel_signup_consents` 테이블 하나와 Auth 가입 트리거를 추가한다. 서버가 버전·동의값을 검증하고 DB 시각으로 기록하며, 본인만 조회하고 클라이언트는 수정할 수 없게 한다. 기존 회원은 유지하고 과거 동의 기록을 만들어 넣지 않는다.
- 트리거 적용 후에는 관리자에 의한 신규 Auth 사용자 생성도 버전·동의 검증 영향을 받는다. 실제 동의가 없는 테스트 사용자에게 동의한 것으로 데이터를 만들어 넣지 않는다. 기존 HOST 계정은 영향을 받지 않는다.
- PGlite의 로컬 PostgreSQL 테스트에서 검증·서버 시각·기존 사용자 보존·RLS·변조 차단을 확인했다. 원격 SQL은 미실행이며 정책 승인과 버전 확정 후 DB 적용 승인을 받아야 한다.

정책의 항목·목적·보유기간 등은 실제 서비스에 맞춰 확정해야 한다. [개인정보 포털의 처리방침 작성 안내](https://www.privacy.go.kr/front/contents/cntntsView.do?contsNo=9)를 참고했다. 현재 초안은 법적 검토나 실제 운영 정책 확정의 증거가 아니다.
