# 로컬이음 참가 신청 및 시연 결제 설계

## 목적

공개된 로컬이음 체험의 모집 회차에 로그인 사용자와 비회원 모두 신청할 수 있게 한다. 신청은 개발 Supabase에 저장하고 접수번호를 발급한다. 입금 화면에는 실제 입금이 불가능한 시연용 가상계좌 표기를 제공하며, 카드 결제는 추후 결제사 연동을 위해 선택할 수 없는 준비 중 상태로 둔다.

## 사용자 흐름

1. 방문자가 체험 상세에서 모집 중인 회차를 고르고 참가 신청으로 이동한다.
2. 로그인 사용자는 현재 Supabase Auth 이메일을 자동 입력하고 계정 ID와 신청을 연결한다. Auth 메타데이터에 이름이 없으면 이름만 직접 입력하게 한다.
3. 비회원은 이름, 이메일을 입력한다. 연락처는 선택 입력으로 두고, 연락 언어·참가 인원·메모와 개인정보 동의를 받는다.
4. 신청 제출은 접수 결과 화면으로 이어진다. 이 화면은 접수번호, 신청 회차와 금액, `DEMO-` 접두어가 붙은 시연용 번호, 유효 시각을 보여준다.
5. 결제 선택 영역에는 시연용 가상계좌를 선택 상태로 보여주고, 카드 결제는 “준비 중”으로 비활성 표시한다. 시연용 번호는 은행이 발급한 가상계좌가 아니며 입금·결제를 확인하지 않는다. 화면에 실제 예약·결제가 완료되지 않았음을 표시한다.

기본 범위는 현재 공개된 시연 체험 12개의 모집 중 회차 전체다. 신청은 접수 상태로 저장되며 결제 또는 참가를 확정하지 않는다.

## 데이터 및 보안

현재 공개 테이블에는 신청 데이터가 없다. 새로 추가할 `lc_applications`는 신청자 정보, `auth.uid()`에서 얻은 Supabase Auth 사용자 ID(비회원은 NULL), 회차 ID, 인원, 연락 언어, 메모, 개인정보 안내 버전과 동의 시각, 고유 접수번호, `PENDING` 상태 및 정원 임시 보류 만료 시각을 저장한다. `lc_application_payments`는 신청별 시연 결제 방법, 금액, `DEMO_ONLY` 상태, 은행에서 사용할 수 없는 가짜 표시 번호와 만료 시각을 저장해 추후 결제사 연결 지점을 분리한다.

브라우저에 공개 테이블 직접 쓰기 권한을 주지 않는다. `lc_submit_experience_application` DB 함수가 로그인 사용자의 ID를 요청 본문이 아니라 `auth.uid()`에서 얻고, 입력 형식·동의·공개 상태·모집 상태·모집 마감·시작 시각·회차 정원을 검증한다. 신청 인원은 1명 이상이며 잔여 좌석을 넘을 수 없다. 회차 행을 잠근 상태에서 `PENDING` 신청의 임시 보류 만료 시각과 인원 합계를 확인해 신청 및 `DEMO_ONLY` 결제 레코드를 원자적으로 만든다. 접수 시점부터 24시간 동안 신청 인원을 정원에 포함하며, 유효 시각이 지난 시연 신청은 잔여 정원 계산에서 제외한다. 시연 입금을 확인하거나 신청을 확정하는 함수는 만들지 않는다. 회차의 최소 모집 인원은 한 신청의 최소 인원이 아니라 회차 운영 기준으로 취급한다.

비회원과 일반 Auth 사용자는 신청 생성 함수만 호출할 수 있다. 직접 SELECT/UPDATE/DELETE는 허용하지 않는다. 본인 Auth 신청은 로그인 사용자만 읽을 수 있고, 호스트는 자신이 소유한 체험의 신청 연락 정보를 읽을 수 있도록 RLS를 둔다. 비회원은 접수 후 결과 화면에서만 결과를 확인하며 공개 조회 API는 만들지 않는다. 관리자 읽기 범위는 현행 ADMIN 역할 정책에 맞춘다.

실제 카드 번호나 은행 계좌번호는 받거나 저장하지 않는다. 개인정보 필드는 신청 확인과 호스트 연락에 필요한 최소 항목으로 제한한다. 개인정보 안내 버전과 동의 시각은 기록하되, 보유 기간은 운영 정책으로 확정해 안내해야 한다. 정식 운영 전에는 만료된 시연 신청의 개인정보 삭제 시점과 담당 절차를 결정한다.

## 구현 범위

- 체험 상세의 선택된 모집 회차 아래에 참가 신청 진입 버튼을 추가한다.
- 참가 신청 화면과 제출 결과를 만들고 Auth 상태에 따라 로그인 사용자와 비회원 흐름을 지원한다.
- 새 신청/시연 결제 테이블 및 원자적 신청 RPC를 검토용 SQL 마이그레이션으로 작성한다.
- 클라이언트 저장소 함수는 기존 publishable key와 RLS/RPC를 사용한다. 서비스 키는 브라우저에 노출하지 않는다.
- 공통 Header, `App.jsx`, Oracle 관련 파일은 수정하지 않는다.
- 카드 결제, 실제 가상계좌 발급·입금 대조, 환불, HOST용 신청자 관리 UI는 이번 범위에서 구현하지 않는다. 다만 호스트 소유 신청 조회 정책은 개인정보 보호와 후속 연락을 위해 준비한다.
- 원격 Supabase에는 검토·승인 전까지 SQL을 적용하지 않는다.

## 고려한 접근

1. 브라우저에서 신청 테이블에 직접 쓰기: 구현은 간단하지만 비회원 개인정보 테이블에 직접 접근 권한이 필요하고 동시 신청 정원 검사를 안전하게 묶기 어렵다. 선택하지 않는다.
2. DB 함수 한 번으로 신청과 시연 결제를 함께 생성: 행 잠금, 정원 검사, 접수번호 발급을 트랜잭션으로 처리하고 PII를 RLS 뒤에 둘 수 있다. 이를 권장한다.
3. 실제 결제사 또는 실제 가상계좌를 먼저 연결: 계약·자격증명·입금 통지가 필요하고 이번 요청의 시연 범위를 넘는다. 추후 별도 승인과 제공자 선정 뒤 진행한다.

## 검증 기준

- 로그인 사용자는 Auth 이메일이 자동 입력되고 제출 결과가 해당 Auth 사용자에 연결된다.
- 비회원은 계정 생성 없이 신청하고 고유 접수번호를 받는다.
- 필수 동의 누락, 모집 종료/마감, 잘못된 인원, 정원 초과 시 저장되지 않는다.
- 동시 신청이 정원을 넘기지 않으며 만료된 시연 신청 인원은 다시 모집 가능하다.
- 신청 결과는 접수 및 결제 미완료 상태를 명확히 표시하고 `DEMO-` 번호를 실제 계좌로 오인하지 않도록 안내한다.
- 카드 결제 버튼은 비활성이고 카드 정보 입력란이 없다.
- 비회원의 공개 SELECT, 다른 Auth 사용자의 신청 열람, 다른 호스트의 신청 열람이 차단된다.
- 관련 단위 테스트, 빌드, 린트가 통과한다. 원격 DB 통합 검증은 승인된 마이그레이션 적용 후에만 수행한다.
