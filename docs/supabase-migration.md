## 전체 수집·변경분 동기화 (최신 운영 상태)

`npm run sync:tourism` / `npm run import:tourism`은 수량 제한 샘플 수집 대신
한국관광공사 국문 `areaBasedSyncList2`를 1,000건씩 마지막 페이지까지 수집합니다.
초기 전체 70페이지, 원본 69,208건 저장을 완료했습니다. 표출 가능 원본은 49,595건이며
현재 여행지 목록은 분류 12인 관광지 12,556곳을 24곳씩 페이지로 표시합니다.
공식 비표출 상태도 원본에 보존하되 목록·검색·일정 후보에서 제외합니다. 기존 리뷰 연결 행을 삭제하지 않습니다.

`travel_tour_source`는 contentid별 원본 JSONB, 수정 시각, 공개 상태, 정규화된 원본 해시를 저장합니다.
같은 내용은 다시 쓰지 않고, 해시가 달라진 행만 공개용 장소·목록 스냅샷과 함께 트랜잭션으로 갱신합니다.
최초 전체 저장 이후에는 성공한 실행의 시작일 하루 전부터 `modifiedtime`으로 다시 조회해 누락을 방지합니다.
반복 조회에서 변경분 후보 10건, 실제 갱신 0건을 확인했습니다. 상세 소개·운영 정보는 목록 API에 없는 항목이므로
최초 상세 진입 시 추가 조회 후 저장하고, 원천 수정 시각이 바뀌면 다시 조회합니다. 모든 상세/사진 API를 69,208번 호출한 상태는 아닙니다.

`travel_tour_sync_state`에 다음 페이지·조회 시작일·처리 건수·오류·실행 잠금을 저장합니다.
중단 후 마지막 페이지에서 재개하며, 페이지 데이터와 커서가 같은 트랜잭션으로 반영됩니다.
동시 실행은 잠금으로 막고, 한도·응답 오류 시 완료로 처리하지 않습니다. 실제 70번째 페이지 재개를 검증했습니다.
일일 호출 한도에 걸리면 중단하고 다음 실행에서 재개합니다.
현재 코드의 `maxPages`는 테스트/수동 배치 경계용이며 기본값은 전체 페이지 처리입니다.

`202610250005_tour_sync.sql`~`202610250007_tour_catalog_search.sql`을 적용했습니다.
최신 법정동 시도 코드와 기존 지역 코드 모두 처리하며, 확인 불가능한 지역은 임의로 채우지 않습니다.
대용량 목록은 서버에서 검색·페이지 나누기를 수행하고, 추천 후보는 작은 공개용 뷰와 1분 캐시를 사용합니다.

## 관광 데이터 초기 수집 기록

`node server/import-tour-catalog.js`로 한국관광공사 API 원본을 먼저 Supabase에 저장합니다.
이번 실행은 실패 0건으로 총 186건(관광지 85, 음식점 51, 숙소 50)을 17개 지역에 저장했습니다.
`comm_place.ext_key=tourapi:<contentid>`로 중복을 막으며 `comm_place_tour_detail`에
소개·주소·좌표·운영정보·이용 가능한 사진·원천 ID·동기화 시각을 함께 보관합니다.
재실행은 같은 원천 ID를 갱신하며 기존 리뷰나 연결된 장소를 삭제하지 않습니다.

현재 `TRAVEL_SEARCH_DATA_SOURCE=database`이며 목록·검색·메인 추천·AI 일정 후보는 저장된
관광공사 데이터만 사용합니다. 여행지 목록은 분류 12(관광지) 85곳을 보여 줍니다.
AI 일정은 저장된 관광지·음식점·숙소를 읽어 LLM에 전달하고 실시간 관광공사 호출을 하지 않습니다.
수동으로 넣은 `sample:*`, `curated:wiki:*` 항목은 기존 링크 보존용이며 새 목록·검색·일정에서 제외합니다.
TourAPI 상세 경로도 저장된 상세가 있으면 먼저 읽습니다. 아직 저장되지 않은 외부 상세는 API로 조회한 뒤 DB 저장을 마치고 응답합니다. 주변 검색은 위치 기반 API 조회를 유지합니다.
이 절이 아래의 초기 점검 및 예시 데이터 확장 기록보다 우선하는 현재 상태입니다.

## 현재 실행 구조

일반 로그인·회원가입과 호스트 인증은 동일한 Supabase Auth 계정을 사용합니다. 로그인 항목은 이메일입니다.
서버는 Supabase Data API로 커뮤니티·찜·나의 여행·저장 여행지·AI 일정 후보를 조회합니다.
`oracledb` 의존성, 연결 설정, SQL 실행 코드 및 이전 DB 생성 스크립트는 제거했습니다.
기존 `lc_*` 체험·호스트 테이블과 데이터는 변경하지 않습니다.

## 환경 설정

`.env.local` 또는 서버 환경에 설정합니다. 실제 값은 저장소에 커밋하지 않습니다.

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
SUPABASE_SECRET_KEY=your-server-only-secret-key
TRAVEL_SEARCH_HISTORY_STORE=supabase
```

서버는 VITE 접두사 없는 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`를 선택적으로 사용할 수 있습니다.
서버 Secret key는 검색 이력 저장·관리용 여행지 가져오기에만 사용하며 일반 API 요청은 사용자 토큰과 RLS로 실행합니다.
프런트엔드에 Secret key를 넣지 않습니다. 브라우저가 보내는 `userId`는 권한 근거로 사용하지 않습니다.
검색 이력은 서버가 서명한 쿠키의 브라우저 범위로 분리합니다. 저장 모드는 `supabase` 또는 `disabled`이며 JSON 파일 저장 경로는 제거했습니다.

## 데이터 이전 및 외부 API

기존 DB의 회원·게시글·여행 데이터를 가져온 작업은 아닙니다. 현재 작업 환경에는 이전 DB 연결 정보나 데이터 내보내기 파일이 없습니다.
기존 자료를 옮기려면 원본 내보내기와 회원 UUID 매핑이 필요합니다. 이전 평문 비밀번호를 Supabase 테이블로 복사하지 않습니다.
현재 프로젝트의 Supabase 계정·체험 데이터는 그대로 유지하며 기본 여행지 8곳만 추가했습니다.

TourAPI와 AI 서비스 키는 DB 전환과 별개입니다. 현재 로컬 설정의 `TOUR_API_SERVICE_KEY`, `CODYSSEY_OPENAI_KEY`는 비어 있습니다.
실제 관광 검색·관광지 가져오기·AI 일정 생성에는 해당 키와 지역별 관광지 후보가 필요합니다.

```sh
node server/import-tour-places.js --per-region=5
node server/import-tour-places.js --apply --per-region=5
node server/sync-tour-place-details.js
```

첫 명령은 미리보기이며 `--apply`를 지정하면 Supabase에 저장합니다.
기존 `setup-places.js`, `setup-likes.js`는 버전 관리되는 마이그레이션 위치만 안내합니다.

RLS 설계 근거: [Supabase 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security).


## JSON·브라우저 저장 제거 (2026-10-25 후속 적용)

`supabase/migrations/202610250002_cloud_itineraries.sql`도 기존 프로젝트에 적용했습니다.
AI 일정은 `travel_itineraries`에 계정별 JSONB 데이터로 저장합니다. JSONB는 Supabase PostgreSQL 컬럼이며 로컬 JSON 파일이 아닙니다.
현재 선택한 일정, 저장한 일정 목록, 변경한 순서는 동일 계정으로 다른 기기에서도 불러올 수 있습니다.
로그인이 필요한 개인 데이터이며 타인의 계정은 RLS가 차단합니다.

브라우저의 기존 `ai-travel-saved-itineraries`, `ai-travel-itinerary`는 AI 일정 페이지에서 로그인하면 자동 이전합니다.
이전 성공 후에만 해당 브라우저 키를 지우고, 형식 오류·네트워크 오류 시 원본을 보존합니다.
같은 일정은 다시 이전해도 중복되지 않으며 기존 서버 일정을 덮어쓰지 않습니다.
로그인 상태와 화면 언어 설정은 앱 동작을 위한 브라우저 설정으로 유지합니다. 별도 JSON 회원 캐시는 제거했습니다.

검색 이력 JSON 파일은 다음 명령으로 원래 브라우저 식별자·검색 시각을 보존하여 이전할 수 있습니다.
원본 파일은 수정하거나 삭제하지 않으며 재실행해도 중복 저장하지 않습니다.

```sh
npm run migrate:json
npm run check:tourism
```

현재 서버의 `server/data/search-history.json`은 없어 이전할 검색 이력은 0건입니다.
로컬·Supabase 실제 프로젝트에서 일정 저장·재조회·현재 일정 전환·타인 접근 차단·중복 이전 방지를 검증했습니다.

## 관광 데이터 확인 결과

후속 여행지 목록 확장: `node server/seed-destinations.js --apply`로 실제 명소 49곳을 추가해
기존 8곳을 포함한 총 57곳을 Supabase에 저장했습니다. 17개 지역에 분포하며 전 항목에 장소별 사진이 있습니다.
새 항목은 `curated:wiki:<pageid>` 외부 키로 중복을 방지합니다. 지역 단위 주소·간단 소개·확인된 좌표와
참고 사진은 장소 상세 데이터에 저장하고, 사진 원본은 `public/images/destinations/`에 포함합니다.
Commons 사진의 작가·라이선스·출처는 목록 및 상세 화면에서 표시합니다. 운영시간·요금은 임의로 채우지 않습니다.
이는 아래의 최초 점검 이후 수동으로 보강한 목록이며 TourAPI 실시간 가져오기 데이터는 아닙니다.

현재 설정의 검색 데이터 모드는 비어 있고, TourAPI 키와 AI 키도 비어 있습니다.
따라서 실시간 TourAPI 데이터를 받아오는 상태가 아닙니다.
Supabase 장소는 기본 8곳(제주 2, 전남 4, 부산 1, 서울 1)이며 TourAPI 가져오기 장소 0곳, 저장된 상세 스냅샷 0건입니다.

| 기능 | 코드에 연결된 출처·조회 |
| --- | --- |
| 관광 검색 | 한국관광공사 KorService2의 `searchKeyword2`, `areaBasedList2` |
| 상세 | `detailCommon2`, `detailIntro2`, `detailInfo2`, `detailImage2` |

조회 대상 항목은 장소명·주소·좌표·지역/분류·사진·소개·전화·운영시간·휴무·주차·요금입니다.
검색 코드에는 관광지·문화시설·축제공연·여행코스·레포츠·숙박·쇼핑·음식점 분류가 있습니다.
실제 관광 검색에는 `TRAVEL_SEARCH_DATA_SOURCE=tourapi`와 `TOUR_API_SERVICE_KEY`가 필요합니다.
기본 장소 8곳과 하드코딩된 화면 예시를 실제 TourAPI 조회 결과로 설명하지 않습니다.

## 회원가입 화면과 테이블 매핑

회원가입 화면은 이름(활동명), 이메일, 비밀번호, 비밀번호 확인을 받습니다.
이름은 앞뒤 공백을 제거한 1~100자로 검증하고 `auth.users.raw_user_meta_data.name`에 전달합니다.
기존 `travel_sync_profile` 트리거가 같은 계정 UUID를 사용해 `travel_profiles.user_name`을 생성합니다.
이메일과 비밀번호는 Supabase Auth가 관리하고 UUID는 자동 생성합니다.
비밀번호 확인은 저장하지 않으며 기존 약관 동의 체크는 화면 입력 검증으로 유지합니다.
비밀번호는 기존 화면과 같이 8자 이상이며 Supabase의 추가 정책에 걸리면 안내를 표시합니다.
가입 응답에 따라 즉시 로그인 완료 또는 이메일 인증 안내를 구분하고, 확인용 비밀번호는 서버로 보내지 않습니다.
프로필을 브라우저에서 별도로 insert하지 않아 인증 계정과 프로필의 중복 생성을 막습니다.
임시 검증 계정으로 실제 Auth UUID·프로필 UUID 일치와 이름 저장을 검증했고, 해당 계정은 정리했습니다.


## 사이트 검색·조회 관심도 (2026-10-25)

`202610250004_site_activity.sql`을 적용했습니다. `travel_site_activity`는 서버 전용 테이블이며
브라우저에는 최근 7일 집계와 여행지 순위만 반환합니다. 기존에 저장된 실제 검색 날짜도 이전했습니다.
그래프의 검색은 성공한 검색 API 요청 수(결과 0건 포함), 조회는 여행지 상세 화면을 연 기록 수입니다.
검색 UI의 중복 요청은 요청 UUID로 중복 저장을 막고, 상세 조회는 브라우저·장소·30분 구간마다 한 번 집계합니다.
검색어·이메일·사용자 UUID를 새 집계 테이블에 넣지 않습니다. 날짜는 Asia/Seoul이며 기록 없는 날은 0입니다.
상단 순위는 관광지의 최근 7일 검색 결과 반환 횟수와 상세 조회 횟수를 같은 가중치로 합산합니다.
반환 횟수는 실제 화면 노출이나 클릭 수가 아닙니다. 커뮤니티 리뷰·예시 관심도 수치는 사용하지 않습니다.
과거 상세 조회는 수집하지 않았으므로 새로 소급 생성하지 않습니다. 집계 실패는 검색 결과 표시를 막지 않습니다.

## 공통 로그인 표시와 로컬 체험 이동

상단 공통 헤더는 Supabase 로그인 상태를 구독하여 이름과 로그아웃을 표시합니다.
이름은 `travel_profiles.user_name`을 우선 사용하고, 프로필 조회 실패 시 Auth의 이름으로 표시합니다.
로그아웃은 상단 한 곳에서 처리하며 호스트 운영센터·회차 편집 화면의 중복 이메일/로그아웃 표시는 제거했습니다.
저장 중인 호스트 작업은 로그아웃을 막고, 저장하지 않은 변경이 있으면 기존 확인 절차를 유지합니다.
상단에는 계정 이름과 로그아웃을 표시하며, 호스트 관리는 로컬 체험 화면의 프로필 관리 링크로 진입합니다.
호스트 진입용 로그인 후에는 일반 회원도 호스트 관리 화면으로 이동합니다.
기존 호스트 프로필이 없으면 본인 이름과 소개를 입력해 생성하고, 이후 실제 저장·수정할 수 있습니다.

`202610250003_host_self_registration.sql`을 적용했습니다. 등록 함수는 로그인한 본인의 UUID만 사용하고,
본인 소유의 비공개 `PENDING` 프로필과 `HOST` 역할을 생성합니다. 중복 등록은 기존 프로필을 반환합니다.
일반 회원에게 관리자 역할이나 승인 권한은 주지 않으며, 타인의 비공개 프로필은 읽거나 수정할 수 없습니다.
승인 대기 중에도 본인 프로필은 수정할 수 있고, 체험 공개와 운영에는 기존 호스트 승인이 필요합니다.
서비스 서버의 계정 정리에 필요한 `lc_hosts` 조회·삭제 권한은 `service_role`에만 부여했습니다.
브라우저에서 계정명과 공통 로그아웃 표시를 확인했습니다.
실제 Supabase 통합 검사에서 생성·저장·중복 방지·타인 접근 차단·승인 변경 차단을 검증했습니다.
