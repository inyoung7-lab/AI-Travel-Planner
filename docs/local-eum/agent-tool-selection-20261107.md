# LOCAL EUM — 모델 도구 선택 구조 및 배포 검토

## 변경 내용

기존에는 서버가 네 도구의 순서를 정하고 모델에는 각 도구의 인자만 요청했다. 새 로컬 코드는 모델에 전체 허용 도구와 이전 결과를 제공하고 다음 행동 하나를 JSON으로 선택하게 한다.

```json
{"action":"tool","tool":"retrieve_local_knowledge","arguments":{"query":"창동예술촌","region":"CHANGWON"},"reason":"지역 안내의 근거를 먼저 확인합니다."}
```

모델은 도구 실행 결과를 받은 뒤 다른 도구·재검색·종료를 선택한다. 종료 형식은 `{"action":"finish","reason":"필요한 근거와 계산 결과가 확보됐습니다."}`다. 프록시의 네이티브 tool-calling 제약으로 일반 Chat Completions를 사용하지만, 도구 이름과 실행 순서는 서버가 지정하지 않는다. 서버는 네 도구만 실행하며 점수·금액을 직접 계산한다.

검색 두 도구는 생략하거나 재검색할 수 있다. 보고서에 표시할 평가·비용 결과는 필수다. 이 결과 없이 모델이 종료하면 부족한 항목을 피드백하고 다시 선택하게 하며 결과를 임의로 채우지 않는다. 기존 보고서·출처 검증과 JWT/HOST/승인/소유권 검사를 유지한다. 모델의 선택 이유는 HOST 화면의 순서가 있는 실행 기록에 표시하고 서버 로그에는 기록하지 않는다.

## 제한

| 항목 | 제한 |
|---|---|
| 도구 실행 | 요청당 최대 6회 |
| 같은 도구 | 최대 2회 |
| 모델의 선택 판단 | 최대 7회 |
| 최종 보고서 | 모델 호출 1회, 선택 판단 포함 총 최대 8회 |
| 루프 전체 시간 | 최대 90초 |
| 모델 요청 1회 | 최대 30초, 남은 전체 시간을 넘지 않음 |
| 한도 응답 | `AGENT_LIMIT` / HTTP 422 |

기존 Edge 인스턴스별 HOST 시간당 12회 제한도 유지한다. 이는 전역 할당량이 아니며 별도 운영 과제다. 개인정보·키·프롬프트·모델 원문은 로그에 기록하지 않는다.

## 실제 검증 결과와 한계

- 코어 테스트를 먼저 변경해 기존 고정 루프에서 11개 실패를 확인했다. 어댑터의 선택·종료·거부 테스트도 기존 코드에서 3개 실패를 확인하고 구현 후 통과했다.
- 함수와 프런트 오류 처리 테스트 **29개 통과**. 순서 변경, 검색 생략·재검색, 조기 종료 피드백, 미허용·복수 도구 차단, 도구별/전체 횟수와 시간 제한, 허위 출처 차단, HOST 소유권·계산 검증을 포함한다.
- 웹 build, lint 및 Deno check/lint 통과. 웹 lint에는 로컬이음 외 기존 경고가 있고 빌드에는 번들 크기 경고가 있다.
- 앞선 원격 함수의 기존 체험·새 아이디어 분석은 HTTP 200(약 12.2초·11.2초)이었다. 이 결과는 **이전 배포 구조의 증거**이며 새 구조의 실제 모델 검증 결과가 아니다.
- 사용자가 이전에 겪은 실패 당시 로그를 확보하지 못해 그 원인은 확정하지 않았다. 오류 안내는 안전한 서버 코드에 따라 설정·DB·권한·모델 응답·한도를 구분한다.
- 새 구조는 로컬 모의 테스트만 완료했다. 로컬에는 AI 비밀키가 없고 서버 비밀키를 로컬/채팅에 옮기지 않았다. 새 구조의 실제 모델 호출은 승인 후 배포된 함수에서 검증해야 한다.

## 원격 배포 승인 범위

대상: **local-eum-dev / rhkaxmqdkztpbljkunxb / Edge Function local-eum-agent**.

변경 소스는 `agent-core.mjs`, `codyssey-client.mjs`, `index.ts`다. 기존 `auth.mjs`, `knowledge.mjs`, `deno.json`도 의존성으로 번들링한다. `verify_jwt = true`와 기존 Edge Secrets를 유지한다. DB 테이블·데이터·RLS·Storage의 변경은 없다. 배포 전 기존 원격 함수 소스/버전을 보존하고, 문제 발생 시 그 소스를 재배포한다. 변경 전후 코드를 로컬 main/hykang 전체 전환으로 되돌리지 않는다.

현재 원격 함수 배포, Git 커밋·Push는 수행하지 않았다. 공식 Supabase MCP는 현재 도구 목록에 없으며 CLI 실행 환경/프로젝트 접근 권한을 확인한 뒤 코드 배포만 수행한다. SQL Editor는 Edge Function 코드 배포 도구가 아니다.

## 배포 후 검증

1. Dashboard에서 프로젝트 이름과 ID를 대조한 뒤 함수만 배포한다.
2. 승인된 HOST로 기존 체험 분석, 새 아이디어 분석, 선택안 상세 기획을 실행한다.
3. 개발자 도구에서 HTTP 200과 응답의 `execution.strategy = model_selected_json_actions`를 확인한다. 이것이 없으면 이전 함수를 호출한 것이다.
4. 실행 기록에서 모델이 선택한 도구 순서와 이유를 확인한다. 모의 테스트의 순서 변경·검색 생략 결과와 실제 모델 결과를 구분한다. 입력이 달라도 모델이 반드시 다른 순서를 선택한다는 뜻은 아니다.
5. 보고서의 평가·비용·근거와 운영안 표시를 확인한다. 분석은 DB를 수정하지 않으며 소개 저장은 기존 HOST 검토·복사·저장 절차를 따른다.
6. 타 HOST 체험 거부, 비로그인 거부, 한도와 모델/DB 오류 안내를 별도로 확인하고 실제 실행 시각과 결과를 기록한다.
