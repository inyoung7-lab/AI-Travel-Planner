# 여행 한걸음 발표자 대본

발표 구성: 20장, 약 10~12분을 기준으로 조정 가능한 대본이다.

## 01. 여행, 한걸음

안녕하세요. 여행 한걸음은 국내 여행지를 찾고 나에게 맞는 일정을 만드는 서비스입니다. AI가 만든 초안을 조정하거나 빈 일정에서 직접 계획할 수 있도록 구성했습니다. 이번 발표에서는 문제 정의부터 구현, AI 활용 방식, 개발 중 피드백과 검증 결과를 설명하겠습니다. 이미지: Ashy Minivet, 설악산, CC0. 출처는 public/images/destinations/credits.json의 9135 항목입니다.

## 02. 여행 계획에서 생기는 부담

문제 정의는 국내 여행을 준비할 때 여러 종류의 정보를 날짜와 이동 순서로 조합해야 한다는 가설에서 시작했습니다. 개발 과정에서도 경남의 먼 도시가 한 코스에 섞이는 문제가 실제로 제기됐습니다. 서비스의 목표는 준비 시간을 줄일 수 있는 흐름을 제공하는 것이며, 시간 단축률은 아직 측정하지 않았습니다. 근거: README.md 문제 정의와 개발 대화의 경남 동선 피드백.

## 03. 대상 사용자

이 세 유형은 실제 인터뷰 통계가 아니라 서비스 설계를 위한 사용자 유형입니다. 여행자를 위한 탐색과 일정 기능, 호스트를 위한 운영과 AI 진단 기능을 구분했습니다. 사용자 수나 유형별 비율을 추정하지 않았습니다. 근거: src/pages/mytrip/ManualTrip.jsx, src/pages/AiItinerary.jsx, docs/local-eum/host-operations-guide.md.

## 04. 서비스 구성

주요 기능은 사용자의 여행 준비 순서에 맞춰 연결했습니다. 찜은 관심 장소 보관이고 일정에 담기는 실제 날짜별 계획에 추가하는 기능입니다. 여행 후에는 일정 하나를 기준으로 전체 날짜를 다시 보고 장소별 리뷰를 작성합니다. 근거: src/App.jsx, server/mytrip.js, src/pages/mytrip/TripHistoryDetail.jsx.

## 05. 여행자의 이용 흐름

사용자는 여행지를 찾고 찜한 뒤 AI 일정 또는 직접 작성 중 하나를 선택합니다. 계획을 받은 뒤에도 장소를 바꾸고 원하는 날짜에 담을 수 있습니다. AI와 수동 일정은 travel_itineraries의 payload를 공유해 나의 여행에서 함께 관리합니다. 근거: src/lib/manualItinerary.js, src/lib/itineraryRepository.js, server/mytrip.js.

## 06. 여행지 탐색

원본 관광정보와 실제 관광지 분류를 구분했습니다. 원본은 여러 종류를 포함하므로 원본 전체 수를 관광지 수로 설명하지 않습니다. 목록은 매번 관광공사 API를 호출하지 않고 Supabase의 저장 정보를 24개씩 조회합니다. 일부 상세 및 주변 정보는 외부 조회가 남아 있습니다. 근거: server/repositories/placeDetailRepository.js, server/sync-tourism.js. 화면: 사용자가 제공한 실제 개발 화면.

## 07. AI 여행 일정

여행 일정 화면은 조건 입력, 날짜별 타임라인, 위치 지도를 함께 제공합니다. 예산과 이동 수단은 사용자의 의도를 전달하는 조건이며 실제 상품 가격이나 도로 이동시간을 검증한 결과는 아닙니다. 현재 새 생성은 한국 시간 기준 오늘 이후 1~5일로 제한합니다. 근거: server/itinerary.js, src/pages/AiItinerary.jsx. 화면: 사용자 제공.

## 08. 직접 만드는 나의 일정

처음에는 AI 일정만 계획의 출발점이었습니다. 직접 계획하고 싶다는 요청을 반영해 빈 일정 생성과 날짜별 장소 담기를 추가했습니다. 별도 임시 테이블 대신 기존 저장 구조를 활용하며 새 수동 일정은 현재 선택된 AI 일정에 영향을 주지 않습니다. 근거: src/pages/mytrip/ManualTrip.jsx, src/lib/manualItinerary.js, server/mytrip.js.

## 09. 여행 기록과 커뮤니티

지난 여행은 실제 방문을 인증한 데이터가 아니라 저장한 일정의 종료일을 기준으로 분류합니다. 같은 여행이 장소마다 반복돼 보이는 문제를 일정 단위 카드와 전체 코스 상세로 개선했습니다. 상세 화면에서 각 장소의 리뷰 작성으로 연결합니다. 근거: server/mytrip.js, src/pages/mytrip/TripHistoryDetail.jsx, server/community.js.

## 10. 로컬 체험과 호스트 운영

로컬 체험의 공개 운영 범위와 데모를 구분했습니다. 호스트의 권한과 체험 소유권을 확인하며 일반 회원이 프로필을 만들었다고 관리자 또는 승인 권한을 얻지는 않습니다. AI 결과는 자동으로 운영 데이터에 덮어쓰지 않습니다. 근거: docs/local-eum/host-operations-guide.md, docs/local-eum/ai-agent-runbook.md, supabase/migrations/202610250003_host_self_registration.sql.

## 11. AI 일정의 검색 증강 생성

여행 일정은 서버가 실행 순서를 정한 생성 워크플로우입니다. 검색 증강 생성은 벡터 DB가 필수라는 뜻이 아니라, 외부의 실제 정보를 검색해 모델 생성의 근거로 활용하는 구조로 적용했습니다. 후보 ID를 제한하고 결과를 다시 실제 장소와 연결합니다. 근거: server/itinerary.js, server/itineraryContext.js, server/repositories/savedTourRepository.js.

## 12. 권역과 여행 날짜를 반영한 추천

기존 방식은 도 단위의 후보를 앞에서부터 잘라 AI에 넘겨 이동 거리가 길어질 수 있었습니다. 이제 세부 지역을 고르거나 가까운 권역을 자동 선택하고, 이동 수단에 따라 반경을 적용합니다. 실제 경남 3일 검증에서는 거제시 내 코스로 구성됐으며 날짜별 최대 구간 직선거리는 약 3.6~5.1km였습니다. 이는 한 샘플 검증값입니다. 근거: server/itineraryContext.js와 실제 생성 검사. 날씨: https://open-meteo.com/en/docs .

## 13. 호스트 체험 AI Agent

호스트 Agent는 일반 채팅으로 도구 인자와 최종 보고서를 순차 생성하는 어댑터입니다. 모델 제공자의 네이티브 도구 호출 지원 제한을 고려한 선택입니다. 도구 실행과 인자 검증, 출처 검증 및 계산은 Edge Function이 담당합니다. 연락처를 모델 입력으로 넘기지 않고, 권한과 소유권을 확인합니다. 최근 추가 실행한 모의 테스트 16개가 통과했으나 이는 모든 실제 모델·언어 품질을 증명하지 않습니다. 근거: supabase/functions/local-eum-agent, docs/local-eum/ai-agent-runbook.md.

## 14. 시스템 아키텍처

웹은 React와 Vite로 구성하고 Supabase Auth 세션으로 인증합니다. Express는 외부 API 키를 보관하고 관광정보 조회와 일정 생성을 검증합니다. 회원의 일정 편집 일부는 RLS가 적용된 Supabase SDK로 직접 수행합니다. 호스트 Agent는 별도 Edge Function 경로입니다. 공개 배포 연결은 별도 수행 범위입니다. 근거: src/App.jsx, server/server.js, server/db.js, src/lib/manualItinerary.js, supabase/functions/local-eum-agent/index.ts.

## 15. 데이터와 기술 선택

기존 Oracle 의존성을 런타임에서 제거하고 Supabase로 인증과 여행 데이터를 통합했습니다. 관광정보 원본은 체크포인트와 변경 해시를 통해 처리합니다. JSONB 일정 payload는 날짜별 코스를 표현하고 optimistic version check로 충돌을 감지합니다. 예약 동기화는 로컬 실행에 의존하므로 공개 운영 환경의 서버 스케줄러는 별도 설정해야 합니다. 근거: server/db.js, server/sync-tourism.js, src/lib/manualItinerary.js, supabase/migrations.

## 16. 개발 중 피드백과 개선

이 표는 실제 개발 대화에서 제기된 요청과 반영 내용을 요약했습니다. 최소 5명의 외부 사용자 설문이나 만족도 조사 결과는 아닙니다. 개발 요청에 대한 반영과 자동 검증은 분리해서 설명합니다. 근거: 대화의 일정·찜·권역·과거 기록·직접 작성·페이지 분할 요청 및 해당 구현 파일.

## 17. 검증 결과

단위 및 통합 검사 결과를 구분했습니다. 실제 DB 검사에서는 임시 계정을 생성하고 일정, 찜, 리뷰와 접근 제한을 검증한 뒤 정리했습니다. 실제 LLM을 호출해 거제시 일정 생성과 저장 및 다시 열기도 확인했습니다. 화면 전체의 클릭 검증은 브라우저 연결 문제로 완료하지 못했습니다. 테스트 수는 서로 일부 중복되므로 독립적인 시나리오 합계로 사용하지 않습니다. 근거: package.json 테스트 스크립트, server/supabase.integration.test.js, server/plannerFlow.integration.test.js, supabase/functions/local-eum-agent/*.test.mjs.

## 18. 팀 역할과 협업

팀 역할은 팀에서 제공한 내용을 반영했습니다. 강하연은 로컬 체험, 최인영은 사진 및 추천, 황재훈은 AI 여행 일정, 김수민은 커뮤니티, 이충훈은 로그인과 데이터베이스 설계입니다. 공통 인증과 장소 ID, 저장 구조를 맞추는 것이 기능 통합의 주요 연결 지점이었습니다. 세부 커밋 기여율은 별도로 산정하지 않았습니다.

## 19. 사용자 검증과 다음 단계

현재 정량 사용자 만족도나 외부 사용자 5명 이상의 결과는 제공되지 않았습니다. 자료 패키지에 참여 코드와 작업별 완료 여부, 설문 및 개선 기록 양식을 넣었습니다. 실제 결과를 기록한 뒤 발표에서 이 장을 업데이트할 수 있습니다. GitHub와 서비스 배포는 이번 자료 제작과 별도로 사용자가 수행하는 범위입니다.

## 20. 여행의 계획과 기록을 한곳에서

여행 한걸음은 근거 있는 AI 초안과 직접 편집을 함께 제공해 사용자가 여행 계획의 최종 선택권을 갖도록 만들었습니다. 탐색부터 계획, 저장과 여행 후 리뷰까지 이어지는 흐름을 구현했습니다. 이후에는 실제 사용자 검증 결과를 바탕으로 개선을 이어가겠습니다. 사진: 서울관광 아카이브, 경복궁, KOGL Type 1. public/images/destinations/credits.json의 6611 항목에 원본 및 라이선스 URL이 있습니다.
